```go
// exitError carries a specific exit code up to run through the error chain.
type exitError struct {
	code int
	err  error
}

func (e *exitError) Error() string { return e.err.Error() }
func (e *exitError) Unwrap() error { return e.err }
```

## 1. Run a subprocess

- **Never `sh -c` with user input.** Pass an argument vector to `exec.CommandContext`: nothing is re-parsed, so `a b; rm -rf /` stays one literal argument. Use a shell only for a constant string you wrote.
- **`exec.LookPath` first**, so a missing tool reads `X is not installed`, not `fork/exec: no such file`. Test with `errors.Is(err, exec.ErrNotFound)`.
- **Always `CommandContext`** with the `ctx` from `main`; its default `Cancel` kills the child. Set `cmd.Cancel` to send SIGINT first so the child can clean up (Windows cannot signal: kill there), and `cmd.WaitDelay` so a child that ignores it is killed after 5 s and its pipes are closed. Without `WaitDelay`, a grandchild holding a pipe open hangs `Wait`. A terminal Ctrl-C already reaches the child (same process group); `Cancel` covers SIGTERM and timeouts. Checked with `go doc os/exec Cmd.Cancel` and `Cmd.WaitDelay` on Go 1.27.2.
- **Stream or capture.** The child's output is not your data: stream it to your **stderr** (one shared writer for both streams is copied serially). Capture only when you need the bytes; `cmd.Output()` also fills `ExitError.Stderr` for the error message.
- **Propagate the exit status** from `*exec.ExitError`. `ExitCode()` is `-1` when a signal killed the child: map that to 1. If `ctx` is done, report "interrupted", not the kill status.
- `cmd.Stdin = env.Stdin` only if the child may read input; `nil` means `/dev/null`.

### How it looks

Streamed (the child's output is on stderr, stdout stays empty), captured, then failures. Exit code 2 is `ls`'s, passed through:

```
$ proc exec -- git --version
step: Running git --version
git version 2.43.0
$ v=$(proc exec --capture -- git --version 2>/dev/null); echo "captured: $v"
captured: git version 2.43.0
$ proc exec -- ls /nonexistent; echo "exit $?"
step: Running ls /nonexistent
/usr/bin/ls: cannot access '/nonexistent': No such file or directory
proc: ls: exit status 2
exit 2
$ proc exec -- nosuchtool; echo "exit $?"
proc: nosuchtool is not installed (not found on PATH)
exit 1
$ proc exec -- sleep 30 &    # then kill -TERM that pid after 1 s
step: Running sleep 30
proc: sleep: interrupted
exit 1
```

A literal argument stays literal: `proc exec --capture -- printf '%s\n' 'a b; echo pwned'` prints `a b; echo pwned`. On a terminal the step line is `🔹 step:` as in ux.md. (The `Running` step line comes from `env.UI.Step`, called before the command starts.)

## 2. HTTP client

- **Own a `http.Client{Timeout: ...}`.** `http.DefaultClient` and `http.Get` have no timeout, so one stalled server hangs the CLI. The timeout is per attempt, not for the whole retry loop.
- **`http.NewRequestWithContext(ctx, ...)`** so Ctrl-C aborts an in-flight request (the `noctx` linter enforces it).
- **`User-Agent: tool/version`** on every request; reuse `buildVersion()` from tool.md.
- **Close the body** on every path and cap what you read (`io.LimitReader`). Check the status yourself: `Do` returns no error for a 404 or 500.
- **Retry only idempotent GETs**, only on 5xx, 429 and transport errors, and boundedly: 3 attempts, exponential backoff from 500 ms, waits capped at 30 s. Honor `Retry-After` (seconds or an HTTP date). Never retry another 4xx (your request is wrong) or anything once `ctx` is done, and wait with `select` on `ctx.Done()`, not `time.Sleep`.
- Log each retry at warn with `slog`. The error that finally surfaces is the last attempt's, printed once by `run`.
- Test with `httptest.Server`: a real listener, so status, header and body paths are all exercised.

→ Read [`assets/recipes/fetch/client.go`](../assets/recipes/fetch/client.go) (104 lines; builds, tests and lints clean).

The command calls `newClient("fetch/"+buildVersion(), c.Timeout, c.Tries, env.Log).Get(ctx, c.URL)` and writes the body to stdout. Four tests, all pass under `-race`, against an `httptest.Server` whose handler counts hits in an `atomic.Int32`, asserts the `User-Agent`, and fails the first `n` requests with a given status (and optional `Retry-After`) before answering `ok`: two 503s then success (3 hits), give up after `tries`, a 404 is hit once, `Retry-After: 1` waits at least 1 s. Tests set `c.backoff = time.Millisecond` to stay fast.

## 3. Bounded concurrency

- **`errgroup` with `SetLimit(n)`** (`golang.org/x/sync/errgroup`, v0.24.0). `g.Go` blocks while `n` workers run, so the loop itself is the backpressure. Never an unbounded `go func()` per item.
- **`errgroup.WithContext`**: the first error cancels `gctx` and `Wait` returns it. Workers must check `gctx` (a read loop, `NewRequestWithContext`) or they run to the end anyway. Stop scheduling with `if gctx.Err() != nil { break }`.
- **After `Wait`, return the parent `ctx.Err()`**, not `gctx.Err()`: `gctx` is always cancelled once `Wait` returns. Without this, Ctrl-C yields partial results and exit 0.
- **No data race by construction.** Preallocate `results := make([]T, len(items))` and let worker `i` write only `results[i]`: no mutex, deterministic output order. Use a mutex only for state that is really shared (the progress counter). Loop variables are per-iteration since Go 1.22, so the closure uses `i` and `p` directly.
- **Validate `n >= 1` at parse time.** Kong calls a command's `Validate() error`; a failure is a usage error (exit 2). `SetLimit(0)` blocks forever.
- **Progress:** one mutex-guarded counter redrawing a single line, only on a terminal (ux.md rule 2). Off a terminal print nothing until the final `ok:` line. Data goes to stdout in input order after the workers finish.
- Always run `go test -race ./...`.

→ Read [`assets/recipes/fanout/sums.go`](../assets/recipes/fanout/sums.go) (127 lines; builds, tests and lints clean).

## 4. Destructive actions

- **`--dry-run` / `-n`** prints the plan to **stdout**, plain (`would remove <path>`, one per line: it is data) and changes nothing; the summary `info:` goes to stderr. Check it **before** confirming, so `--dry-run --yes` still changes nothing.
- **`--yes` / `-y`** skips the confirmation. It never overrides `--dry-run`.
- **Without `--yes`: ask on a terminal, fail otherwise.** "Terminal" means stdin **and** stderr are TTYs. If not, return an error naming `--yes` and exit **2**. The missing confirmation is required input that was not supplied, which is a usage error (SKILL.md rules 5 and 10), like a missing argument. Never assume yes without a human, never hang on a prompt in CI.
- **Declining is exit 1** (`aborted, nothing removed`): the request was valid, the work was not done. Ctrl-C at the prompt (`huh.ErrUserAborted`) is also 1.
- **The prompt goes to stderr** (`WithOutput(stderr)`), keeping stdout clean for the `removed <path>` lines. This is tui.md's `confirm` plus that one call; `ACCESSIBLE=1` swaps in plain line prompts.
- Print each removal and a final `ok:` count. Stop at the first failure.

→ Read [`assets/recipes/clean/clean.go`](../assets/recipes/clean/clean.go) (86 lines; builds, tests and lints clean).

Tests call `run` with `bytes.Buffer`s, which are never terminals, so the non-TTY path is covered for free: `--dry-run --yes` leaves all 3 files and prints two `would remove` lines; no flag exits 2 with `--yes` in stderr and removes nothing; `--yes` removes the two `.tmp` files and keeps `keep.txt`. ### How it looks

Non-interactive (stdout is only the plan or the result; `info:`/`ok:` are stderr):

```
$ clean clean --dry-run DIR
info: Dry run: 2 files would be removed, nothing changed
would remove DIR/a.tmp
would remove DIR/b.tmp
$ clean clean DIR </dev/null; echo "exit $?"
clean: refusing to delete without confirmation: pass --yes (or --dry-run to preview)
exit 2
$ clean clean --yes DIR
ok: Removed 2 files
removed DIR/a.tmp
removed DIR/b.tmp
```

On a terminal without `--yes` (captured in a pty and rendered through a VT emulator; the prompt is a huh form on stderr):

```
┃ Remove 2 files from DIR?
┃
┃               Yes     No

←/→ toggle • enter submit • y Yes • n No
```

Answering `y` leaves `removed DIR/a.tmp`, `removed DIR/b.tmp` and `✅ ok: Removed 2 files`. Answering `n` prints `clean: aborted, nothing removed`, exits 1 and leaves all three files. `clean -n DIR` on a terminal prints the two `would remove` lines and `🔵 info: Dry run: 2 files would be removed, nothing changed`, with no prompt.
